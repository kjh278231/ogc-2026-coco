## 🟡 계획 (우선순위순)

0★ (다음, 이제 입증된 최우선). **탐색 중 incumbent 스냅샷 진짜채점 (monotonic 가드)** — reserve-인하 REJECT(완료 참조)가 직접 입증: **모든 '더 많은 search' 레버(reserve 인하·adaptive-reserve·긴 budget)가 proxy-drift 벽에 막힘** — 환전한 search가 prob_20을 더 나쁜 true-obj basin으로 보냄(portfolio도 증폭). 지금은 끝에서 2개(탐색 전/후 best)만 진짜채점. 이걸 **탐색 도중 여러 체크포인트의 best를 진짜채점**으로 늘려 best 제출 → "더 search ≥ 덜 search" **단조 보장** → prob_20/prob_7(+48%)/prob_6 drift 회귀를 구조적으로 차단. 이게 되면 (a) reserve 인하로 Gurobi headroom 환전, (b) adaptive-reserve(−9.1%) 안전 활성, (c) portfolio 워커도 단조 → 전부 잠금해제. **주의**: proxy 순위 top-K만 모으면 true-good이 누락되니 **시점 체크포인트** 기반. 설계 doc 권장.
0★b (MIP-repair 회귀 제거 — 입증 대기). **입력 기반 MIP-repair 게이트** — front-load MIP은 손실 인스턴스(prob_37 +10.9% 등)에서 탐색 8s를 헛되이 강탈. **싼 신호로 분기해 안 도울 인스턴스는 skip → pure-upside 회복.** 신호 2종: ① **GO=Z2/Z3 여유**(선호 vs 부하균형 긴장; 프록시 = bay수 m, a_pref의 Z2 불균형), ② **SKIP=Z1 난이도**(면적 utilization 높으면 MIP의 Z1-무시 배정을 repair가 못 잡음; [[train-tardiness-is-geometric]]). **가장 신뢰도 높은 방식 = 값싼 MIP probe**: MIP solve 자체는 싸다(~1-2s, 배정문제) — 짧은 TL로 풀어 surrogate(Z2+Z3) 격차 `(S_pref−S_mip)/S_pref`를 보고 임계 미만이면 repair(비싼 ~4s) 자체를 skip → 손실 인스턴스 비용 8s→~2s. **선결: cheap-falsification** — 40개에 신호값 vs 실제 best-of 승패를 찍어 분리되는지 확인(probe ~1분, 정적feature 공짜) 후 임계 추출·게이트화. 분리 안 되면 포기.
0★c (single-use 라이선스 후폭풍 — 검증 필요). **portfolio recombine 손상 재검증** — [[gurobi-single-use-license]] 때문에 T≥180 portfolio의 워커 4개 중 **먼저 라이선스 잡은 1개만 recombine 성공**, 나머지 3개는 조용히 no-op(크래시 X, 탐색 다양성은 유지). −28/−35% T=300 검증은 **Gurobi 전환 전(ortools, 동시 CP-SAT 무제한)** 측정이라 현재 실제 효과 불명. 옵션: (a) 현 상태 재측정(워커 3개 recombine 없이도 net 이득인가), (b) Gurobi 접근 직렬화(락/순번), (c) 워커는 recombine 없이 탐색만 + master가 1회 recombine. **eval timelimit 미공개**라 T≥180이 실제 경로면 영향 큼.
0. **full-20 재확인 + 기본값 플립** — 스택에 numba 기본 on(=−28.5% 추가). 전 20개로 새 합산·회귀 재확정 후 mask-search/자동조절/numba를 default on으로 코드 플립 + submission 폴더 갱신.
0c. **guided swap move** — 현재 이웃은 relocation(a→b)뿐, swap 없음. exit-time 신호(extract_tardiness의 `exited`, 현재 버려짐)로 tardiness↔slack / 무거움↔가벼움 / 상호선호불일치 3계열 top-K 쌍만 평가(랜덤 X). relocation이 못 넘는 Z2 미세조정·포화 bay 교환·더 깊은 local optimum 도달. **behavior-changing → eval-count 고정 obj-delta로 판정**(swap도 1 eval로 카운트, 공정). **품질 검증은 incremental-eval 없이 지금 가능**(full-eval+eval-count 결정론), incremental-eval은 배포 속도 곱셈기. 가장 싼 첫 probe = guided-swap Destroy 프로파일(포트폴리오 멤버). 설계 `docs/swap_move_experiment_design.md`.
1. **adaptive R (입력 기반 R4/8/16 자동선택)** — instance마다 최적 R 다름(prob_3은 R16까지 개선, prob_20은 R4로 충분). 입력에서 싼 신호로 판단: over-rejection 수렴(knee) / footprint·AABB 면적비 / 크기·예산. 먼저 측정: 전 20개 oracle-best R + 예측신호 상관 → 규칙화. (eval-제한적이라 거친 instance에 낮은 R = 더 빠름 = 더 좋음.)
2. **남은 속도 (eval-제한적이라 큰 objective 전환)** — (a) **mask precompute ~39% 가속**(shapely 래스터화 → numba point-in-poly/matplotlib path, supercover 안전성 재검증 필수), (b) **find_slot_mask 스캔 coarse numba화**(현재 호출당 → 통째 jit로 경계비용 제거).
2b. **C++ packing kernel 실험** — 전체 C++ 포팅이 아니라 `solve_bay` 하위 hot kernel(`masks_overlap`, `find_slot`, `find_slot_mask`, 이후 `_local_mask`)만 native로 옮겨 Numba cold-start를 제거할 수 있는지 검증. **pure speed → fixed-eval bit-identical 필수**, native packaging 허용 여부 먼저 확인. 설계 `docs/cpp_packing_kernel_experiment_design.md`.
3. **prob_3 회귀 원인 규명** — eval-count 무관(numba로도 불변). R/basin 문제로 추정.
3. **재실험 #3: H2 search→recombine→search 루프 under mask-search** (얇은 AABB pool이 폐기 사유였음). **이번 진단(아래 완료)으로 약화**: 실제 사이클 수가 어려운 instance(prob_13/14/20)에선 60초 1회·300초 1~2회뿐(climb가 루프 예산을 통째로 먹어 비수렴). 작은 instance만 12~83회. 즉 "정작 중요한 instance엔 루프 안에 recombine 끼울 자리가 거의 없음" → 하려면 사이클 기아부터 풀어야.
4. **탐색 중 incumbent 스냅샷 진짜채점** (어긋남 보정 — **자동조절 채택의 관문, 최우선**) — 지금은 끝에서 2개(탐색 전/후 최선)만 진짜 점수로 비교. 이걸 **탐색 도중 여러 시점의 최선 답 스냅샷**으로 늘려서 전부 진짜채점하고 best 제출. 그러면 "더 탐색"이 "덜 탐색(=이른 스냅샷)"보다 절대 나빠질 수 없음 → **단조 보장 → prob_7(+48%)·prob_6 회귀를 잡음.** (주의: proxy 순위 top-K만 모으면 true-good이 proxy 순위 낮아 누락될 수 있으니, **시점 체크포인트** 기반이 안전.) 이게 되면 자동조절(−9.1%)을 안전하게 켤 수 있음.
2. **`find_slot` 추가 가속** (numba 기본형 ~2× 확보 후) — 호출당 오버헤드 제거: `ov_boxes`를 numpy로 사전계산/버퍼 재사용, 또는 `solve_bay` 단위로 더 굵게 jitting해 경계 비용 분산. (behavior-invariant, 평가횟수 고정으로 검증.)
3. **polygon "상금" 측정** — `SOLVER_NOPOLY=1` vs 기본, full-20 @ T=180. 차이 = polygon이 지금 회복하는 양 = "더 나은 기하 테스트"가 노릴 상금의 하한. 싸다. 4번 진행 여부를 가름.
4. **거의 정확하면서 빠른 기하 테스트** (멀티박스/래스터) — 탐색과 최종을 한 기준으로 **통일** → 어긋남 제거 + AABB가 못 보던 맞물림 배치까지 탐색. 큰 보상·큰 위험. **보수적 유지 필수**(겹치는데 안 겹친다고 하면 실격 = feasibility). 2번 상금이 크면 진행.
5. **병렬 재시작 모음** (multiprocessing, ≤4코어) — 독립 ILS 여러 개 동시에 → 진짜 점수로 best-of. 탐색 중 노는 3코어 활용. 4로 캡(`os.cpu_count()`는 cpulimit 환경에서 못 믿음). 1번과 곱셈 효과.
